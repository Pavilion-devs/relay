## Absolute expiry and cost

At approval time generate an exact UTC deadline, between 30 minutes and 24 hours from launch preparation. Never reuse stale parameters. The generator rejects past or longer deadlines. A direct CloudFormation invocation can bypass this local check, so use the reviewed parameter generation path and inspect the timestamp immediately before execution.

Two controls use the same timestamp:

1. An AWS EventBridge Scheduler one-time `ec2:StopInstances` invocation, scoped to this instance, with five retries within one hour. The execution role's trust is constrained to this account and schedule group.
2. A host expiry check installed **before** Docker setup/storage waits, run at boot and every minute. Docker and Relay startup also run the check. It requests an orderly host shutdown after expiry. EC2 shutdown behavior is explicitly `stop`.

These reduce exposure; they are not a guaranteed dollar cap. A failed AWS invocation or host shutdown still needs operator response. No notifications or alarm delivery have been configured. This is an operator-supervised rehearsal; confirm shutdown in the AWS API. Do not restart after expiry or update the stack to extend it without a new reviewed deadline. Updating CloudFormation user data does not rerun first-boot setup automatically.

The checked base estimate is **$0.6742 for 24 hours**: t3.small $0.0209/hour, IPv4 $0.005/hour, and 20 GB gp3 at $0.08/GB-month (730-hour accounting). S3 storage/requests, identity use, transfer and tax are additional. The proposed **separate $5 total hosting allowance** provides headroom; the previously approved model-evaluation allowance is separate. No model inference or SES sends are part of this launch. The release archive is about 0.092 GB. Existing account resources are outside this incremental estimate.

After stop, the 20 GB disks still cost about $1.60/month until termination/cleanup. After stack deletion, the retained 12 GB data disk costs about $0.96/month; retained S3 objects/versions also cost money. This plan requests cleanup of only the newly created synthetic rehearsal resources after collecting evidence. Retain policies prevent accidental data deletion during rollback or stack deletion; explicit cleanup follows the inventory below.

## Launch sequence after separate hosting approval

1. Recheck release and template hashes against `docs/aws-launch-review.json`. Verify AWS account/profile, AMI ownership/architecture and zone. Install the official Session Manager client plugin locally; it was not present at preparation time. Set the absolute deadline and generate fresh parameters:

   ```sh
   uv run python -m scripts.prepare_aws_launch --parameters .data/aws-launch-parameters.json --ami ami-0e34b50e714a297f1 --zone us-east-1a --expiry YYYY-MM-DDTHH:MM:SS
   ```

2. Create a uniquely named CloudFormation **CREATE change set**, using this template and parameters, `CAPABILITY_IAM`, and a project tag. Inspect its resource list. It must create only this private rehearsal infrastructure. Execute it only within the approved hosting scope. Persist stack ID, parameters, account, resource IDs and outputs under `.data/` before proceeding. A CREATE change set does not itself start EC2 billing; executing it does.
3. Wait for stack completion and inspect the enabled AWS shutdown schedule/target/role. A completed stack does **not** mean bootstrap passed: no CloudFormation readiness signal is installed. If schedule creation fails or rollback leaves a running host, stop that exact host immediately and inventory retained resources.
4. Through SSM, require `/etc/relay/host-prepared`, successful cloud-init, the expected EBS volume serial, correct mounted filesystem UUID, encrypted volumes, Docker/Compose versions, active expiry timer and outbound reachability. The bootstrap formats only the newly created blank data volume selected by its EBS serial. It refuses any disk signature; do not rerun it on a retained disk.
5. Upload only the verified archive to the new bucket at `release/<archive-sha256>/release.tar.gz`, using server-side AES256 encryption. Record the object version. Fetch it on the host with the instance role and compare the **outer SHA-256 to the laptop's recorded value before extraction**. Internal checksums alone are not provenance. Extract into a new root-owned mode-0700 directory with `tar --no-same-owner`; run `bash deploy/install-release.sh VERIFIED_BUNDLE_DIR NEW_BUCKET_NAME` from it.
6. The installer checks inner hashes, loads the exact image, creates a fresh volume identity and synthetic database, writes nonsecret Cognito configuration and enables services. It refuses an existing installation. If interrupted, inspect partial state; do not delete the runtime file and blindly retry initialization. Do not copy the laptop database. Record the generated volume identity privately.
7. Stop the laptop API only after checking its process identity, then start the SSM port-forwarding session using `AWS-StartPortForwardingSession`, remote and local port 8765. Verify localhost `/ready` and Cognito login. Provision only explicitly scoped synthetic memberships via the existing admin/invitation workflow; logging in alone must not grant workspace access.

## Evidence required before calling this cloud-tested

- Real remote backup and manifest appear in the new private bucket, encrypted; forced upload failure does not refresh readiness. Use synthetic data only.
- IMDSv2 supplies the expected instance-role identity inside the container. API, worker and maintenance retain non-root/read-only settings.
- Cognito login and membership authorization work through the tunnel.
- Restart API/worker and reboot the host; verify disk UUID, workspace and job state persist, then fresh readiness returns. A stale worker heartbeat must fail readiness.
- Run a complete synthetic driver failure → approved replacement → pickup → receipt. This deployment starts with model calls disabled; record whether each input was operator-supplied rather than claiming live model extraction.
- Download a selected S3 backup and manifest through the operator, verify checksum, restore offline under quarantine, record synthetic reconciliation and verify recovery. The host role intentionally cannot download the backup itself.
- Verify the final AWS stopped state and collect expiry/systemd evidence. Do not label the AWS timer effective based only on template validation.

Public HTTPS, real participant access, production deliverability, unattended alerting, and practitioner evidence remain separate work.

## Teardown inventory

Before deletion, capture `describe-stack-resources` and outputs with their exact IDs, and export the synthetic audit/backup evidence needed locally. Never select resources solely by a broad account-wide name match.

| Resource | Stop behavior | Stack-delete behavior | Explicit final cleanup |
| --- | --- | --- | --- |
| EC2 host / 8 GB root | Compute stops; root remains billed | Instance terminates, root deleted | Confirm termination/root removal |
| Automatically assigned public IPv4 | Released on stop | Released | Confirm no allocated Elastic IP was created |
| 12 GB data EBS | Retained and billed | Retained intentionally | After evidence export, delete only recorded available volume |
| S3 bucket and TLS policy | Retained and billed | Retained intentionally | Delete recorded synthetic object versions/delete markers/multipart uploads, then bucket |
| Scheduler / group / execution role | Remain | Deleted | Confirm gone; retained one-time schedule also consumes quota |
| Host role/profile, VPC, subnet, routes, security group, gateway | Remain | Deleted | Confirm all recorded resources removed |
| Local release/evidence | No cloud charge | Unaffected | Keep private evidence locally |

Stop Relay and the EC2 instance before deleting the stack, so volume detachment does not race active SQLite writes. Review `DELETE_FAILED` resources, and also review retained resources after a failed CREATE/rollback. Do not delete the existing Cognito, SES, SNS or SQS infrastructure. Do not prune unrelated Docker images or volumes.
